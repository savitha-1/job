## Public ATS discovery interfaces audited 2026-11-25

- [SmartRecruiters Posting API](https://developers.smartrecruiters.com/reference/v1listpostings) exposes public company postings. The adapter fetches one detail record only after an observed posting URL identifies its requisition; it does not fetch every job detail on a board.
- [Workable careers API guidance](https://help.workable.com/hc/en-us/articles/115012771647-Using-the-Workable-API-to-create-a-careers-page) documents the public careers endpoint used for published job data. The authenticated administrative API is not used.
- [Personio open positions](https://developer.personio.de/docs/retrieving-open-job-positions) documents the public XML job feed. Application URLs are taken only from a visible official page, never guessed from the XML.
- Recruitee and Teamtailor API access requires employer credentials ([Recruitee](https://support.recruitee.com/en/articles/1066282-api-documentation), [Teamtailor](https://docs.teamtailor.com/)); BambooHR has no documented unauthenticated listings API used here. These fall back to public HTML/browser extraction, subject to robots policy and human gates.

The adapters do not reuse external source code. They follow public API documentation, retain observed board identifiers and require evidence connecting the board to the employer.

## Techniques, alternatives, evidence

- Browser traversal is a bounded prioritized frontier, with persistent URL/depth/parent, attempts, host budgets, checkpoint records and in-progress recovery. Public links are prioritized by careers/jobs wording. This is a breadth-limited prioritized queue; it is not Crawljax's event-driven state exploration and does not click controls.
- DOM fingerprints are independent 64-bit SimHash over normalized visible-ish text trigrams. Graph edges retain URL transitions; distinct fingerprints are counted as approximate page states. This favors cheap duplicate detection over exact DOM snapshots, but no labeled crawl set yet quantifies the false-merge rate.
- Dynamic pages are explored with Playwright. Robots policy is checked fail-closed when unavailable. Browser requests are same-origin only, page visits have per-host and per-run budgets, forms are never submitted, and human gates become checkpoints. DNS is not pinned and browsers are not OS-network isolated; do not expose this code as a multi-tenant service.
- Company leads may originate from supplied career URLs, Common Crawl indexes, ATS APIs, or public GH Archive exports. A GitHub organization or a historical archive URL is only a lead, never a verified employer/vacancy.
- Technology signals are deterministic token matches in public GH event metadata and rendered job pages. They are evidence hints, not inferred skills or proof of employer adoption.
- A small live comparison ran ATS keyword filtering and deterministic ranking on the same 800 postings: the first 20 keyword matches contained 0 heuristic India/worldwide signals; the first 20 of the eligibility-aware ordering contained 12. This uses the same unvalidated deterministic eligibility labels, with zero human labels, so it is a ranking illustration and not a precision claim. No labeled benchmark supports a measured accuracy gain over BM25, ATS-only, RRF, graph ranking, or embeddings.

## Continued global-discovery implementation (2026-11-24)

- Added bounded public feed adapters for Arbeitnow DE/UK, Remote OK and Jobicy. Feed records are source observations, not official employer vacancies or direct application URLs. The current report records source credit and links for attribution.
- The live worker reads one capped GH Archive hour and resolves at most 15 account names against GitHub's public organization API. Both event activity and API org profiles remain unverified company leads. The bounded live run resolved 8 org profiles, verified 0 employers, and verified 0 vacancies.
- The new retrieval score is deterministic, alias-aware and field-weighted (title/tags/description). It is not BM25 or a semantic embedding. The modest exact URL de-duplicator merges only identical company+listing URL sightings across provider feeds and preserves all feed names; near-duplicate requisitions remain separate.
- Eligibility checks include role title, location and description. A country-specific location is not promoted by generic worldwide boilerplate. Exact India mentions are evidence signals, not proof that the role exists at the employer or that the provider has not gone stale. Only official-source active vacancies with direct links contribute to the strict fully eligible count.
- In a bounded Common Crawl probe, the current index registry resolved, but two serial domain index queries returned HTTP 504. No records were counted from those failed queries. In a public Playwright probe, 7 pages loaded on 3 company domains, 3 career pages were found, 0 structured JobPosting entries were found, and one site presented a human-verification checkpoint.
- No third-party source code was copied. The registered upstream techniques remain alternatives; no PageRank, probabilistic identity linkage, embeddings or bandit scheduler is claimed to improve this live slice without independent labels.

### Additional employer-authored hiring source (2026-11-25)

- Inspected the actual `elvongray/hnhiring` upstream API and parsing implementation at [`src/api/algolia.ts`](https://github.com/elvongray/hnhiring/blob/master/src/api/algolia.ts), [`src/utils/parseJob.ts`](https://github.com/elvongray/hnhiring/blob/master/src/utils/parseJob.ts), the technology dictionary and parser tests. Its [`LICENCE.md`](https://github.com/elvongray/hnhiring/blob/master/LICENCE.md) declares MIT. No source code or private contact details were copied. The upstream uses Algolia's `author_whoishiring` tag for monthly threads and `story_<id>` for comments; this integration independently consumes those public endpoints, keeps only direct children of the current monthly story, extracts role headers and link `href`s, redacts email/phone text, and never promotes a thread URL to an application URL.
- The live November 2026 Algolia response contained 378 comments, 239 top-level comments, 110 parsed top-level engineering role claims, of which 56 matched the configured candidate-role retrieval. Forty-six of the 56 had at least one outbound link. Three links were attempted in a bounded, robots-aware check; none satisfied the strict matching Schema.org employer + title + explicit application URL gate. The trial did not establish active vacancies, verified employers, direct applications, or India eligibility.
- Upstream HN parsing uses heuristics for seniority, remote status, employment and technologies. We did not import those labels because defaults can infer onsite/full-time when absent; unknown remains unknown here. Broad technical matching also requires a role-title gate and contextual Go/Golang evidence.
